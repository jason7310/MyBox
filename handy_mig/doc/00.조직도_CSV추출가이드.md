## 3. [심사숙고] 실제 부서/사용자와 삭제 부서/사용자 분리 방안

### (1) 데이터 상의 삭제 여부 확인 결과
- **부서 (`MG_DEPT`)**: `DELETED` 컬럼 (부서 상태)
  - `DELETED = 0` : 정상 사용 부서
  - `DELETED = 1` : 폐지/삭제 부서
- **사용자 (`MG_USER`)**: `DELETED` 컬럼 (사용자 상태)
  - `DELETED = 0` : 정상 재직자
  - `DELETED = 1` : 휴직자 (핸디 표준 STATUS = '2')
  - `DELETED = 2` : 퇴직자 (핸디 표준 STATUS = '4')

### (2) 왜 반드시 '별개'로 진행해야 하는가?
1. **관리자 화면 업로드 오류 방지**:
   - 상위 부서가 없는 삭제 부서나 폐지된 부서 트리가 정상 부서와 뒤섞이면 트리 계층 생성 오류(`상위부서 미존재`)가 발생합니다.
   - 퇴직 사용자가 폐지된 부서 코드를 참조하고 있으면 사용자 업로드 자체가 실패합니다.
2. **전자결재/기록물철 마이그레이션과의 연계 정합성**:
   - 과거 5~10년 전 결재 문서를 이관할 때 기안자, 결재자(PARTICIPANT), 기안부서가 시스템에 아예 없으면 문서 열람 시 작성자 정보가 공란으로 뜨거나 오류가 발생합니다.

### (3) 실무 권장 처리 프로세스
- **Step 1 [정상 부서 등록]**: `dept_normal.csv` (`ISUSE = '1'`)를 `ADD`로 먼저 업로드하여 실제 운영 조직도를 구성합니다.
- **Step 2 [직위/직급 등록]**: `pos.csv`, `rank.csv`를 `ADD`로 업로드합니다.
- **Step 3 [정상 사용자 등록]**: `user_normal.csv` (`ISUSE = '1'`)를 `ADD`로 업로드합니다.
- **Step 4 [삭제 부서 / 삭제 사용자 처리 - 선택]**:
  - **방안 A (DEL 일괄 반영)**:
    - 과거 이관 데이터 정합성을 위해 일시적으로 등록 후 삭제 상태로 변경해야 하는 경우, `dept_deleted.csv` 및 `user_deleted_del.csv` (`*operation = DEL`)를 별도로 업로드합니다.
  - **방안 B (폐지부서 / 퇴직자 전용 부서 하위 ADD 유지 - 전자결재 이관 권장)**:
    - 관리자 화면에서 최상위에 `[폐지부서]` 및 `[퇴직자부서]`를 1개씩 생성한 후,
    - 삭제 부서와 퇴직자를 해당 부서 하위의 `ADD`로 등록하여 로그인/결재권한은 차단하되 과거 문서 조회 시 정상 노출되도록 유지합니다.
  - **방안 C (⭐ 무조건 전체 선등록 ALL-ADD ➔ 결재 이관 ➔ 오픈 직전 원터치 후처리 삭제 - 프로젝트 표준)**:
    - **1단계**: `dept_all_add.csv` 및 `user_all_add.csv` (또는 DB 직접 적재)를 통해 정상/폐지/재직/퇴직 불문 전체를 `ADD`로 선등록합니다.
      * 결재문서 이관 중 모든 부서 및 사용자 ID가 100% 매핑되어 더미(`000000000`) 결손을 원천 방지합니다.
      * 퇴직자는 패스워드 `!`, 보안/결재등급 0으로 안전 처리됩니다.
    - **2단계**: 전자결재 6단계 고속 적재 및 정합성 전수 검증 수행.
    - **3단계 (오픈 직전)**: `./build_and_run.sh org-post-delete` (`08.ORG_POST_DELETE_UPDATE.sql`)를 1회 실행하여 폐지부서와 퇴직자를 `STATUS = '4'`(핸디 표준 삭제)로 원터치 일괄 변경합니다.
      * 기존 이관 결재문서의 결재선 정보는 100% 보존되면서, 신규 결재선 및 조직도 트리에는 폐지부서/퇴직자가 깔끔하게 숨겨집니다.

## 8. ⭐ 오픈 당일(D-Day) 조직도 증가분(Delta) 추출 가이드

### (1) 핵심 원칙: DEL 완전 배제 (ADD / MOD만 허용)
- **오픈 당일 장애 방지**: 사전 이관 후 오픈 직전까지 발생한 변경분을 반영할 때, `DEL`(부서폐지/퇴직)이 일괄 적용되면 기존 결재문서 열람 권한 결손 및 진행 중 결재선 에러가 발생할 수 있습니다.
- 따라서 증가분은 **`ADD`(신규 등록)와 `MOD`(정보 수정)**만 선별 추출하며, `DEL` 처리는 오픈 후 안정화 단계에서 수작업 또는 후처리 스크립트로 격리 진행합니다.

### (2) 추출 대상 파일 7종 (조직도 전 영역 커버)
1. **`pos_delta.csv`**: 직위 증가분 (신규 직위 `ADD` / 명칭·서열 변경 `MOD`)
2. **`rank_delta.csv`**: 직급 증가분 (신규 직급 `ADD` / 명칭·서열 변경 `MOD`)
3. **`dept_delta.csv`**: 부서 증가분 (신규 부서 `ADD` / 부서명·상위부서 이동 `MOD`)
4. **`user_delta.csv`**: 사용자 증가분 (신규 입사자 `ADD` / 부서이동·승진 `MOD`)
5. **`group_delta.csv`**: 그룹 증가분 (신규 공용/수신처/결재선 그룹 `ADD` / 명칭 변경 `MOD`)
6. **`group_member_delta.csv`**: 그룹멤버 증가분 (신규 그룹 배속 멤버 `ADD`)
7. **`auth_delta.csv`**: 사용자 권한 증가분 (신규 부서장 `S1`, 접수담당자 `D1`, 발송담당자 `Da`, 문서관리자 `D4` 등 `ADD`)

### (3) 실행 절차 (폐쇄망 콘솔 기준)
```bash

./build_and_run.sh org-delta-check

# 2단계: 증가분 7종 CSV 일괄 자동 추출 (Forge)

# 추출 산출물 확인
ls -l output/csv/*delta*.csv
# -> output/csv/pos_delta.csv
# -> output/csv/rank_delta.csv
# -> output/csv/dept_delta.csv
# -> output/csv/user_delta.csv
# -> output/csv/group_delta.csv
# -> output/csv/group_member_delta.csv
# -> output/csv/auth_delta.csv
```

### (4) 핸디 관리자 화면 일괄등록(E/F) 순서 (외래키 무결성 보장)
관리자 콘솔(`조직/사용자 관리` -> `일괄등록`)에서 반드시 아래 순서대로 업로드해야 참조 오류가 발생하지 않습니다.

```
[1순위] 직위 (pos_delta.csv) & 직급 (rank_delta.csv)
   ↓ (신규 직위/직급이 먼저 등록되어야 신규 입사자/승진자 등록 가능)
[2순위] 부서 (dept_delta.csv)
   ↓ (신규 부서가 먼저 등록되어야 사용자의 소속 부서 매핑 가능)
[3순위] 사용자 (user_delta.csv)
   ↓ (신규 사용자가 등록되어야 그룹 멤버 및 권한 부여 가능)
[4순위] 그룹 (group_delta.csv) -> 그룹멤버 (group_member_delta.csv)
   ↓
[5순위] 권한 (auth_delta.csv)
     (신규 부서장 S1, 접수담당자 D1 등 결재 핵심 권한 즉시 반영)
```
